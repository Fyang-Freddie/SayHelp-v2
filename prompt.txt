SayHelp 智能客服系统

我要用 Superpowers 模式开发一个完整、可运行、可验收的电商智能客服系统 SayHelp。请以资深全栈工程师、Agent/RAG 工程师的角色协助我，按本文完成需求澄清、系统设计、实施计划、开发、验证和交付。本文是最终系统需求，不是按章节逐次演示的教程。不要只完成一个聊天 Demo，也不要把中间阶段的占位方案当作最终成果。

一、需求优先级与总原则

1. 产品名称、客服品牌、页面标题、默认话术和文档统一使用 SayHelp；真人坐席身份应如实展示，不冒充真人。
2. 本文中的最终要求覆盖原有分章节限制：最终系统包含多轮 Agent、混合 RAG、正式意图识别、上下文摘要、MCP、可观测性、数据飞轮及主题分类微调。分阶段交付只用于管理依赖，不得成为漏做功能的理由。已确认：去掉章节限制，整合十章已定义的最终功能；仅在排除项中提及、没有具体定义的额外功能另议，不自动扩大范围。
3. 使用已有真实知识、历史对话、业务数据和训练数据。订单、商品、物流、在保、退货进度必须连接真实数据源或已有数据文件；不得随机生成业务数据，不得用模拟人工接入、假工单或虚假评估数字通过验收。真实接口、文件或授权缺失时说明具体阻塞，向我索取，不能假装接通。测试隔离可以采用明确标注的测试替身，但不可作为业务运行数据和最终集成验收证据。业务数据存放在\sayhelp\knowledge_db。
4. 意图识别固定使用 jev 模型，独立于主力 Agent 模型。不得未经确认改成主力模型，也不得自动回退到其他模型。jev 的准确标识、服务地址、调用协议和配置由我确认，不自行猜测或更正拼写。
5. 微调使用已有 train.jsonl、val.jsonl、test.jsonl，存放在\sayhelp\sft_dataset，训练、评估、导出和独立推理相关代码集中在 sft/，与客服系统代码分离。
6. 先梳理已有仓库、数据与接口，再设计。对影响架构、权限、真实接入和验收的未知项，集中列出问题及建议方案供我审核；确认前不把建议当成既定需求。无争议的工作继续推进。
7. 引用规则已确认：每个回答末尾呈现来源说明。知识回答附 [1]、[2] 等可点击文献编号，业务回答附可点击的查询记录编号；没有可引用依据的闲聊、澄清、拒答等话术明确注明“无外部文献”。不得伪造文献，也不得把无关文献附到回答后凑编号。
8.所有的api等相关配置存放在.env中，按需使用，在系统全部结束之后，可以删除没有用的。数据库是我原来创建的，如果有需要可以创建新的 。

二、固定技术栈与工程结构

1. 后端：Python、FastAPI、SQLAlchemy；MySQL 通过 Docker 启动，作为业务数据、消息、知识原文和审核记录的权威存储。
2. 模型与工具：LangChain、PromptTemplate、with_structured_output、@tool、trim_messages；LangGraph 实现确定性 Workflow、State、add_messages reducer、持久化 checkpointer、interrupt/resume。
3. 模型接入：直连所配置的上游模型端点，应用侧统一使用 OpenAI 兼容协议，服务地址、模型名称、密钥等通过 .env 配置。提供 .env.example，不提交真实密钥。GPT、Claude、DeepSeek、Ollama 等仅在相应接入端确实兼容时可配置切换，不虚构原生协议兼容性。主力模型、jev、改写/摘要/裁判模型的职责和配置分别明确。
4. 知识检索：BGE-M3 嵌入；Milvus 2.5 或以上兼容版本，锁定版本需支持原生 BM25、中文 analyzer 和 hybrid_search；dense + BM25 使用 RRF 融合；bge-reranker-v2-m3 精排。
5. MCP：官方 Python SDK，自建物流和售后两个独立进程的 Server，使用 Streamable HTTP；客户端使用 langchain-mcp-adapters 的 MultiServerMCPClient。
6. 可观测性：自部署开源 Langfuse，链路数据保留在自有服务器。
7. 前端：原生 HTML、CSS、JavaScript；实现登录、聊天、历史会话、交互卡片和管理后台，不擅自替换前端框架。
8. 主题分类：哈工大讯飞 RoBERTa-wwm-ext，全参微调；独立推理服务的具体形式在 transformers 服务或 ONNX 等方案中确认。该分类器不承担实时意图识别。
9. 工程模块至少区分：API、认证授权、业务服务、Workflow/Agent、模型配置与 Prompt、工具注册/执行、MCP Client/Servers、知识入库与检索、会话与摘要、飞轮与评估、数据模型与迁移、前端、测试、sft/、dev-notes/。
10. 任何涉及具体库、框架、API 的实现，先通过 Context7 MCP 查询最新官方文档及与锁定版本相匹配的接口定义。不要凭记忆写接口。工具不可用时明确说明，不能谎称已查阅。固定选型出现冲突或不能实现时，先给出证据和备选方案让我审核，不擅自替换。

三、端到端主流程

用户登录 → 提交问题与可信登录凭证 → 后端验证身份及会话归属 → 保存用户原话并构建本会话上下文 → 指代消解与 Query 归一 → jev 意图识别 → 代码确定性分流 → 必要的订单选择/真实数据查询 → 必要的 Query 扩写、RAG 与置信度检查 → 主力 Agent 或固定话术/人工服务选项 → 受控工具调用与人工确认 → 流式回答、引用与交互卡片 → 消息、状态、调用轨迹及日志落库 → 异步摘要、反馈归集、知识审核、评估和主题归类。

图中明确划分实时同步节点、可中断交互节点和异步任务。用 State 贯穿流程，用 checkpointer 持久化并恢复执行。消息数据库用于历史原文和查询，checkpoint 用于图运行状态；设计一致性、失败恢复和重复请求处理，不能互相替代。

四、登录、身份注入和权限

1. 提供登录界面。聊天页面的用户身份来自登录态，每轮请求携带可验证的认证凭证，后端解析得到可信 user_id、角色和权限。不得仅信任前端提交的任意 id。
2. 用户身份作为运行时隐藏参数，由后端注入工具执行上下文。user_id、认证令牌、权限上下文不出现在模型可见的工具参数 Schema、System Prompt、模型消息或工具结果里。模型只填写业务参数，不能指定或修改操作者身份。
3. 认证上下文与模型上下文分离；在内置工具和 MCP 调用边界均做白名单和脱敏处理。验证实际发往模型的请求体，确认隐藏身份未泄露。
4. 用户只能查询自己的会话、订单、工单及对应引用。会话历史、订单选择、工具调用、反馈、interrupt/resume、引用查看都必须校验归属；不能只在页面隐藏按钮。
5. 管理员可访问管理后台，查看模型调用历史、工具审计、知识审核、低置信度问题、评估趋势和主题分布；具体可见字段及数据范围先确认。普通用户不能访问管理员接口。
6. 工具可见性与执行权限分开控制。即使模型提出调用，执行引擎仍独立鉴权。读写权限按本地规则判定，不能相信模型或外部 MCP Server 的自我声明。
7. create_ticket 是已明确的写工具。修改用户数据、实际退款提交等写能力，须先确认业务接口、权限、确认方式和幂等规则，再纳入统一执行引擎。

五、会话、流式交互与上下文管理

1. 对话接口支持多轮及 SSE 流式输出，按上游 token/delta 到达即时推送，不等整段生成结束才发送；前端逐字呈现，并说明上游 delta 可能包含多个 token。聊天采用用户/客服消息气泡排布，在本轮客服气泡中显示实际调用工具名称的轨迹小徽章，历史回载仍能查看。工具执行、检索、中断等待等阶段发送状态事件，最终回答流式呈现；约定文本、状态、引用、卡片、错误和完成事件，处理连接中断及重试，避免重复消息或重复写操作。
2. PromptTemplate 模板化管理角色、业务红线、负面知识、证据约束和输出格式；禁止编造政策和工具执行结果；将“不承诺到账时间”等业务红线明确写成禁止行为，不能只禁止编造、却允许模型自行承诺。
3. 用 with_structured_output 将售后描述提取为订单号、诉求类型、期望方案等固定字段，缺失项明确为空或待补充，不瞎编。
4. 历史记录保存完整用户和客服原文。侧栏按新到旧列出当前用户会话、首问预览和已摘要标记；点击回载原聊天框并继续聊；点击“新聊天”创建独立会话，旧会话仍保留。
5. 当前聊天区域可滚轮滑动，下方中央设置“返回最新”按钮，点击定位到最新聊天气泡；用户查看旧消息时不要被新 token 强行拉回。
6. 提供 GET /api/conversations 和 GET /api/conversations/{id}/messages，做分页和归属校验。侧栏加载失败不阻断当前聊天。
7. 当前会话上下文采用三层结构：
   - 最近层：保留原文，不做摘要或改写。
   - 中间层：用户原话不动；客服回复只保留开头几十个字；大块工具结果压缩为一行可追溯标识。
   - 最远层：异步形成事实和诉求摘要，摘要独立存表，只追加，不反复重写旧摘要。
8. 用 summary_upto_msg_id、layer1_from_msg_id 标记分层边界，原始消息不搬移、不覆盖。沿用原 DDL 的明确边界：id ≤ summary_upto_msg_id 属于已摘要区；summary_upto_msg_id < id ≤ layer1_from_msg_id 属于中间层；id > layer1_from_msg_id 属于最近层。layer1_from_msg_id 表示原文区之前的边界消息，不按字段名猜成含起点的区间；初始化空值语义在设计中补齐。避免重复注入或漏消息。conversation_summaries 保存 seq、from_msg_id、upto_msg_id、content、created_at，并保证同一会话 seq 唯一。
9. 中间层超过 token 预算才触发异步摘要，不以消息条数代替用量。摘要提炼真实商品、订单号、用户明确提供且确有业务需要的手机号、明确诉求、待解决事项；不保留寒暄、不创造事实。敏感信息按用途最小化处理。每段以几十到一两百字为目标，不能为了字数删除必要事实。
10. 摘要任务不得阻塞当前回复，需处理重复触发、失败重试、并发覆盖边界和提交一致性。触发时固定本批中间层边界，成功后 summary_upto_msg_id 追到该批 layer1_from_msg_id；不能覆盖未处理的并发新消息。旧摘要仅作背景，不再次有损合并；过多摘要如何适配窗口，先提出保留和选取策略供确认。
11. 模型上下文顺序原则：稳定的 system 人设/红线/工具定义 → 中间层精简消息 → 最近层原文 → 当前用户问题 → 合为一条背景上下文消息的早期摘要与检索证据。摘要不得额外占一个会被上提合并的 system 消息；最后的背景材料以明确标记的上下文注入，不能伪装成用户指令。具体角色及工具调用消息配对须符合上游协议。
12. State.messages 使用 add_messages reducer，各节点返回新增消息；完整历史随 checkpoint 保存，调用模型前另建精简上下文，不修改原始历史。使用 LangChain trim_messages 配合分层规则和 token 预算整理精简输入；裁剪必须保留合法的工具调用及结果配对。
13. 预算从模型窗口倒推，扣除 system、工具定义、证据、摘要、输出预留、安全余量、当前输入和 ReAct 瞬时峰值；历史预算取期望保留轮数预算与实际剩余预算的较小值，最近层 70%、中间层 30%，明确整数取整规则。启动时检查是否至少容纳一轮，容量不足明确报错。优先使用实际 tokenizer，并校准中文估算。
14. 分层压缩按真实用量触发，装得下就不压。可用以下配置验证压缩路径：MODEL_CONTEXT_WINDOW=18000、MAX_OUTPUT_TOKENS=2000、MAX_USER_INPUT_TOKENS=2000、MAX_AGENT_STEPS=3、TOOL_RESULT_MAX_TOKENS=1200、RERANK_TOP_K=5。原验收参考值为滑窗 5650、最近层 3954、中间层 1695。必须保留这些值作为对照，并用最终模板、tokenizer、工具定义、固定开销和取整规则重算，给出差异说明；原文未提供完整计算参数且两个分层数合计比总值少 1，不能硬编码或伪称完全复现。若因此需修改验收值，先提交计算表让我审核。
15. 已确认本次上下文管理针对当前会话。跨会话长期记忆、用户画像、语义检索历史与重要度记忆作为额外功能另议，不替代已定义的三层上下文方案。

六、指代消解、jev 意图识别和确定性分流

1. 指代消解使用 LLM，结合当前会话摘要与近期历史，将“它能退吗”“刚才那个订单”等补全成独立可理解的问题。已完整的输入原样透传，指代不明时澄清；保留原话、改写结果和采用的上下文以便追溯。
2. 同步完成口语归一，保持原始诉求和约束，不添加用户未表达的条件。
3. 意图节点用 jev 的 Prompt 分类路线，不训练新的意图分类器；jev 在该节点仅判断意图，严格只输出 intent、confidence 两个字段的可校验 JSON：{"intent":"类别","confidence":0.0}。枚举物流、订单、商品咨询、退款退货、售后、投诉、闲聊和其他；提供边界 few-shot；结构错误、超时和低置信度有明确兜底，不强塞类别。
4. 分类置信度与检索 evidence_confidence 分开存储、校准和使用；不要把模型自报置信度当作天然准确概率。意图节点不负责搜集全部槽位，也不生成业务回答。
5. 路由规则写在代码中：
   - 商品咨询：强制检索知识，置信度足够后进入主力 Agent。
   - 退款退货：获取当前用户真实订单 → 必要时订单选择 → Query 扩写 → 强制检索政策 → 置信度检查 → Agent 基于订单和政策判断。
   - 售后：按 ch6 的正式版要求，与退款退货一致采用订单 → Query 扩写 → 强制政策检索 → 置信度检查 → Agent 的确定性子流程，相关业务查询通过售后 MCP 工具完成，不擅自增加跳过政策的分支。
   - 物流、订单：直接进入 Agent，通过真实业务工具查询，不套用无检索证据的 RAG 置信度闸。
   - 投诉：返回安抚话术及独立的“转人工”“建工单”选项，不进入主力 Agent，不自动执行动作。
   - 闲聊：意图识别后使用固定 SayHelp 话术，不再调用主力生成模型；不能宣称这一轮完全没有模型调用。
   - 其他：使用澄清或能力边界话术，不猜业务动作。
6. Query 扩写仅用于退款退货、售后等需要的检索场景，输出 {"queries":[...]}；多查询检索后去重融合。简单 FAQ 不扩写。同义词扩展只作用于查询，知识库不重复存多份。
7. 缺订单号时调用有权限的真实订单列表，通过 LangGraph interrupt 向前端展示订单卡片；用户选择后校验订单归属并 resume。无订单或接口失败如实说明，不能猜订单。
8. 退款表单提供固定退款原因类目的下拉选择框，由用户自行点选；意图节点和主力 Agent 都不以追问退款原因作为继续对话的前置条件。其他必要的需求澄清由主力 Agent 完成，意图节点只判断要做什么。实际提交接口和写权限需确认；不得仅凭展示表单就声称退款已提交。

七、知识入库、混合检索、置信度与引用

1. 对真实 Markdown 政策、商品 FAQ、售后手册等做标题结构感知切分；超长段递归切分，块间添加重叠，重叠裁到最近句号，不留半截话；遇到没有句号的超长文本或特殊格式时明确切分规则并验证语义完整性；大表按行拆分时每块复制表头。
2. 定时将真实历史客服对话分批交给 LLM 抽取问答对，先进入 qa_extraction_staging，再整体去重并按质量规则入库。记录来源批次和来源会话，防止模型错误答案未经核验污染知识库；审核规则需明确。
3. 每块包含 category、questions、answer，三者拼接为向量化文本。FAQ 和抽取 QA 使用真实问法；政策手册用章节标题作为 questions，上级标题路径作为 category。
4. 元数据包括 section_path、content_type、is_key_clause、prev_chunk_id、next_chunk_id，并补足引用需要的文档标识、版本、位置和来源地址。原有四类元数据不进入向量文本，但可用于过滤、溯源和条款上下文恢复。
5. MySQL knowledge_chunks 是原文权威源，Milvus knowledge 是检索索引。先写 MySQL 并标 pending，再向 Milvus 按稳定主键 upsert，成功后回填 vector_id 并标 done。中断、重复运行及并发重试不产生重复；知识更新或删除也要保持索引一致。
6. 最终 query_faq 使用混合检索，保持外部入参出参契约不变，内部检索策略升级不影响调用方；确实无法保持时先说明原因并提交变更让我审核，不自行扩展契约。SQL LIKE 和纯向量仅作为可复现基线，不作为最终能力。记录同一真实评估语料上“邮费是多少”的 LIKE 漏召回与语义检索改善；若现有数据使 LIKE 已能命中，如实报告，不为了复现教程预期删改真实数据。
7. Milvus 原生 BM25 文本字段配 BM25 函数，中文使用内置 chinese analyzer；dense 和 BM25 各召回 Top-50，通过 hybrid_search + RRF 融合，再用 bge-reranker-v2-m3 精排至 Top-10。这些数量可配置，测试配置不能悄悄变成生产配置。
8. 支持品类等元数据先过滤再检索。多查询结果去重保留来源；重要条款可结合相邻块补全。组装证据时将最相关片段放在首尾，保持可读顺序和编号稳定。
9. 在知识检索后、主力 Agent 生成前设置正式 evidence_confidence 闸，综合精排 Top1 相关性、有效证据数量、Top1/Top2 分差等信号；阈值用标注评估集校准，不拍脑袋，也不能直接把原始 reranker 分数当概率。
10. 证据不足时立即返回明确兜底或拒答，并写 low_confidence_questions；不先流式输出不可靠答案再撤回。生成侧还需以 useful 等结构化内部标记自评证据是否足以回答；useful=false 时拒答并以 source=self_check、附理由写入问题池，标记可不单独持久化。对用户释放实质答案前完成关键检查；如何兼顾流式体验、结构化自评和延迟，在设计中说明。
11. System Prompt 明确只能依据有效证据和工具结果回答，不能把检索到的指令当作系统指令。退款资格的判断与实际退款执行分离，不能做超越政策或接口能力的承诺。
12. 回答使用 [1]、[2] 等引用编号，并在回答后列出对应来源。编号映射到本轮证据快照、chunk、章节路径及文档版本；点击可查看原文和跳转定位，历史回答仍能追溯当时依据。
13. 已确认纯业务回答引用授权可见的真实查询记录，在回答末尾编号列出，点击展示对应结果和查询时间；不将查询记录冒称政策文献。无依据的固定话术注明“无外部文献”。混合回答分别标明文献与查询记录类型，编号不得冲突。

八、主力 Agent、统一工具执行与 MCP

1. 使用 LangGraph 中的主力 Agent 节点实现受控 ReAct/工具循环：模型提出调用 → 引擎校验鉴权 → 工具执行 → 结果回灌 → 继续或收敛。简单问题可一步完成，复杂问题可先查订单再查物流。缺信息主动澄清。
2. 设置最大步数、token 总预算、超时、重复无效调用检测和停止条件，达到限制时可理解地收敛。不要求展示模型隐含推理过程，只展示必要操作状态和工具轨迹。
3. 按原要求先手写一遍不依赖 Agent 框架的最小工具循环（调用 LLM、有工具申请则执行并回灌、无工具则收敛），验证后再用 LangGraph 重构；保留最小可运行示例与前后对应说明，最终运行路径统一采用 LangGraph，不重复维护两套生产逻辑。
4. 内置工具使用 LangChain @tool 装饰器定义，工具包括 query_order、query_product、query_faq、create_ticket，以及 MCP 物流轨迹、在保查询、退货进度等。订单与商品连接真实数据；物流由物流 MCP 接管，旧内置 query_logistics 退出注册清单，避免重名。
5. 注册中心统一登记工具名、描述、JSON Schema、来源和本地权限规则。内置工具在启动时注册，支持扩展注册；MCP 工具动态发现并更新，每轮取得可用清单。新增工具不改 Agent 核心代码，Server 端新增工具并重启后客户端可重新发现，无需重启客服服务。同一注册/权限版本内，模型可见工具定义保持稳定排序和序列化；注册或授权变化时更新版本并重建前缀，同一轮内工具 Schema 使用一致快照；执行权限仍在每次执行和 resume 时重新校验，不能用旧权限快照放行已撤销权限，也不能为保留缓存而忽略新工具或权限变更。
6. 调用前统一验证类型、必填字段和取值范围。校验失败转成结构化工具结果回灌模型，允许修正或追问，不仅抛异常。
7. 隐藏身份只能由引擎注入。业务参数也需验证资源归属和数据访问范围，不能靠模型承诺正确。
8. 所有工具统一处理超时、重试、错误与结果格式。仅瞬时网络故障可按策略重试；空结果和参数错误不重试；写操作默认不自动重试，超时状态不能假定“未执行”。
9. 区分参数不合法、业务无结果和真实故障；结果只保留回答必需字段，内部枚举转换为可理解内容，JSON 中文不转义，禁止输出认证凭证和隐藏身份。
10. tool_audit_logs 记录 conversation_id、tool_call_id、工具名、builtin/mcp 来源、MCP Server、脱敏参数、结果摘要、状态、错误、重试次数、耗时和时间；成功、失败、超时、校验拦下和权限拒绝都记录。审计表不挂外键；审计写入失败不反向阻断工具，但应告警并具备可追踪的补偿路径。
11. 两个 MCP Server 使用真实数据源、独立进程部署；故障隔离、鉴权传递和客户端动态发现机制需说明。工具用途声明不可信，写权限由本地白名单决定。

九、建工单、转人工和前端确认

1. 转人工与建工单是独立能力，按钮彼此不绑定。除投诉固定分支外，主力 Agent 判断适合人工处理时也可在回复中提出转人工或建工单建议，可只给一个或同时给两个；建议只呈现独立按钮，不自动转接或写工单。用户未选择时不自动执行，可以继续正常聊天。
2. 转人工必须连接真实坐席系统或已确认的真实人工工作台。区分等待接入、已接通、失败、结束状态；只有真实接通后才展示已转接成功，不显示虚构真人问候。
3. 聊天中明确要求建工单时，Agent 核对工单类型、问题描述等必填项，不足则追问；齐全后申请 create_ticket，由执行引擎 interrupt，向前端推送预览卡片和“确认提交”“取消”。
4. 确认请求与当前用户、会话、待执行参数、工具调用绑定，防止篡改、过期确认、重复点击和跨会话 resume。服务端校验后执行一次，写 tickets 并返回真实工单号；取消不写入，按权限拒绝记审计并注明用户取消。
5. 投诉分支的“建工单”按钮可作为用户主动授权入口；只有按钮已明确展示提交内容且必要字段齐全时，点击才等价于确认。信息不齐仍须补齐，不得借这条路径绕过校验。该差异在 UI 和接口契约中写清。
6. 工单确认、订单选择和退款原因表单均支持等待、取消、恢复和失败状态；刷新及重连后不能重复执行已完成的写操作。

十、数据模型与持久化约束

最终迁移必须覆盖以下实体，并保留原需求的字段语义；可以补充必要索引和版本字段，但不能无说明删除关键能力。统一 InnoDB、utf8mb4；执行中文 DDL 前正确设置连接字符集。

1. 用户/认证/角色权限：结构按现有身份系统确认，避免重复造账户源。

3. conversations：用户归属、处理状态、创建时间、摘要投影、summary_upto_msg_id、layer1_from_msg_id。

6. 事后 👎 从原消息所属轮次回捞检索证据，不能拿当前最新检索结果代替；该轮未检索则明确为空。其他采集失败须区分“未检索”和“快照丢失”。
7. 每条回答左下角显示 👍/👎。反馈成功后点亮选择、显示“已反馈”并锁定；后端保证幂等，不只依赖前端。👎 对应用户问题进入问题池。
8. 飞轮流水线：原话标准化成 FAQ 式问题 → 生成仅供审核的示例答案 → 由 LLM 判断与待审问题是否语义相同（不能只用字符串相等代替） → 合并或新建 review_queue → 人工审核 → 核准答案经统一知识入库流程写 MySQL/Milvus → 更新检索可见状态 → 回归评估。

10. 审核后台展示标准化问题、出现次数、示例答案、状态，详情可看原始问题和当时证据，帮助区别“知识缺失”和“检索失败”。通过时填写核准答案；驳回记录理由。向量化尚未完成时不能显示“已可回答”。
11. 自动评估定时及手动执行，指标落 eval_runs，展示至少两轮可比趋势、退化情况和运行配置。
12. 忠实度编造个案进入 faith_cases，按 eval_id 一题一行；再次发生更新最新答案/原因/证据快照并增加 seen_count。已解决或无需解决的个案复发时恢复未解决，保留历史处置时间用于提示复发。
13. citations 保存当轮提供给生成模型的证据全集及编号映射，区分“提供了哪些”与“答案引用了哪些”。标已解决或无需解决必须填写处置说明，退回未解决清空当前处置说明。
14. 后台包含模型调用历史、工具审计、知识审核、低置信度详情、评估趋势、编造个案和主题分布；具体管理员权限范围由我审核。

十二、主题分类微调与 sft/ 隔离

1. 使用已有 train.jsonl、val.jsonl、test.jsonl，先核对路径、编码、字段、标签分布、去重和集合交叉污染。保留原要求：训练/验证/测试按 80/10/10 分层，各类别尽可能保持比例。先检查已有三份文件是否符合；符合则直接使用，不重复拆分；不符合或小样本多标签无法精确分层则报告实际比例和原因，向我确认保留现状还是重划分，未经确认不重划也不悄悄取消比例要求。
2. 不因为某类数据不足就让大模型凭空生成模拟问题补足。报告真实数据缺口并提出采集方案。保留原文的训练集增强要求：仅基于真实训练样本做同义词替换和句式微调，保持业务事实、诉求与标签，记录父样本并复核质量；只能扩训练集，不能污染验证/测试集。不将这些变换用作“虚构新业务事实、模拟数据补量”的借口。若某种变换需要生成原文没有的事实，停止该变换并请我审核。
3. 清洗包括脱敏、格式统一、错字处理，保留原始数据及可追溯转换记录。
4. 全系统维护唯一权威术语表，以退换货、物流、尺码、发票四类领头；每一类都必须配一句边界说明，不能只给近邻示例。17 类为：退换货、物流、尺码、发票、质量问题、运费、优惠活动、价保、支付、订单修改、库存补货、商品信息、保修维修、账号、会员积分、评价、其他。
5. 边界：维修归保修维修，退货归退换货；运费管费用，物流管货物运输；价保指补差价，优惠活动指券和满减。定义“其他”与具体标签是否可共存，交由我审核。
6. 多标签按句子真实表达的诉求标注，不多打、不漏打。例如“买大了想退”应涵盖尺码和退换货。采用大模型按术语表预标、人工抽审的路线，已有高质量标注不擅自覆盖。
7. RoBERTa-wwm-ext 全参微调，配适用于多标签的训练目标、阈值选择、正则化和早停；验证集用于模型与阈值选择，测试集仅做最终评估，不用于调参。不得擅自改为 LoRA/QLoRA 或用它替代 jev。
8. 输出每类精确率、召回率、F1，补充 macro/micro 指标和每类二元混淆矩阵；多标签任务不能误用单标签互斥混淆矩阵。人工复核错判样例并解释边界问题。
9. sft/ 内包含数据说明/校验、标签规范、清洗、预标审核流程、训练配置、训练入口、评估、导出、独立推理服务、报告与使用说明。客服系统通过清晰接口调用，不依赖训练运行环境。
10. 分类器在旁路按批量运行，低置信度问题达到已配置的批量触发条件时执行归类，结果写 topic_classifications；实时对话主链路不调用它，也不通过逐轮异步请求变相调用它。服务和任务具备批次、版本及失败重跑机制。
11. 后台展示各主题问题数；多标签统计可能超过去重问题总数，页面必须说明统计口径。

十三、评估与整体验收

先基于真实资料建立带 ground-truth、难度梯度和 query 类型分桶的评估集，固定版本；可人工编写真实业务测试问法，不能伪造业务事实。质量阈值、规模、延迟和资源目标由我审核，不预先宣称达到未测量指标。

A. 登录与权限
- 登录后可聊，每轮身份可验证；伪造 user_id、越权读历史/订单/引用、越权调用及跨会话 resume 均失败。
- 检查发送给模型的真实请求，隐藏身份、密钥及权限参数未进入模型可见内容。
- 管理员能查看授权信息，普通用户不能访问管理接口。

B. 聊天与历史
- curl 能验证 SSE 实时 token/delta 推送；浏览器能看到气泡逐字输出、工具状态、工具名称徽章及最终引用。
- 多轮上下文连贯，结构化售后信息可解析且缺失字段不编造。
- 新聊天、历史切换、完整回放、滚动和“返回最新”可用；反馈只提交一次。

C. 意图、指代与分流
- 使用真实多轮样例验证物流 → 退款 → 物流切换，检查 jev 调用及 JSON。
- 模糊指代可正确补全或澄清，未知问题归其他；投诉不进主力 Agent，闲聊不调用主力生成模型。
- 退款/售后按订单 → 扩写 → 政策 → 置信度 → Agent 执行，缺订单时真实订单选择可恢复。

D. RAG 与引用
- 对比纯向量、纯 BM25、混合、混合加 Rerank 四策略，报告 Recall@K、MRR、Faithfulness，并按 query 类型分桶。
